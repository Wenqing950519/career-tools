# ④ opportunity-catch — 抓機會

**形態**：純 skill（跑在使用者自己的 Claude/ChatGPT，用其 web search）
**階段**：投哪裡 ／「履歷有了，我要去哪找實習／競賽」
**架構重量**：零後端、零維運。爬蟲服務是獨立 v2 專案（見附錄），做好後接入，不擋上線

## 目的

讀使用者的求職摘要（來自 resume-composer）＋ 意向 → 用 AI 的 web search 搜尋**當下最新**的實習／職缺／競賽 → 去重 → 依他的方向與硬條件排序 → 每項附「為什麼適合你」「對得上你哪段經歷」「截止日」「要小心什麼」。

**不做**：自動投遞、代登入求職平台、任何投遞建議以外的動作。

## 雙模式

啟動時第一個問題：「你現在要找的是？」

### 模式 A：實習／職缺
- 來源：104、1111、Yourator、CakeResume、LinkedIn 的公開頁面 + 站內搜尋 URL 模式 + web search
- 產出欄位：職稱、公司、地點／遠端、關鍵要求、對上使用者哪段經歷、缺什麼（連回 skill-gap）、連結、（可得時）截止日

### 模式 B：競賽
- 主來源：**BHuntr 獎金獵人**（`bhuntr.com/tw/competitions` + 大學／大學生 tag）——covers 八成
- 長尾：web search（`site:edu.tw`、`site:gov.tw` + 競賽／徵件／黑客松 等關鍵詞組合，見 sources 參考檔）
- 產出欄位：競賽名、主辦、**報名截止**、資格（大專生可否）、獎金、組隊需求、為什麼適合、官方連結

## 核心紀律（寫進 skill references）

1. **時效第一**：截止日已過的一律丟棄；查不到截止日的標「⚠️ 截止日未確認，點官網確認」；**寧可少列，不列死的**
2. **Discovery 與 Verification 分離**：聚合平台／搜尋結果拿來發現；截止日、資格、獎金等關鍵事實**必須回官方來源確認**，並標明「此欄來自：官網／聚合站」（沿用競賽架構文件的 source evidence 原則）
3. **Lazy verification**：先淺層列 8–12 個候選 → 使用者挑 2–3 個 → 才深入官方頁面與簡章查證細節。不對全部候選做深查（省 token、省時間）
4. **排序理由必須引用使用者的話**：「排第 1 因為你提到『粉專三個月 200→900』，這個職缺主要工作就是社群經營」——不給無法追溯的分數
5. **硬條件先殺**：地點、身分資格（大專生／應屆）、語言要求不合的直接濾除並說明；偏好（「想要遠端」）只影響排序不淘汰（governance §7 精神）
6. **去重**：同一機會出現在多來源時合併為一筆，保留官方連結為準

## 輸出格式

繁中清單（每項一張卡的資訊量）＋ 結尾一個固定標題的總結區塊：

```
## 本次結果摘要
搜尋時間：2026-08-17
模式：競賽
候選數：10（已濾除 3 個過期、1 個資格不符）
建議先看：#1、#3（截止最近且匹配度說得出理由）
下一步：選定要投的機會後，用 offercheck 做最後確認 → [入口頁連結]
```

## 與前後階段的接口

- **輸入**：resume-composer HTML 的「複製求職摘要」文字塊（教育／能力／經歷一句版／意向）；沒有履歷的人也可用，skill 會先花三個問題建立最小意向（方向、地點、身分）
- **輸出 → offercheck（僅職缺模式）**：拿到 offer 後附「用 offercheck 評估這個」的一鍵素材（公司名 + 職缺名 + 連結）。**競賽模式不導向 offercheck**——offercheck 的適用範圍是 3–6 個月實習／工作 offer 的去留決策，競賽不是 offer；競賽模式的結尾改為截止日行動與簡章細查邀請

## 驗收

- 貼求職摘要 + 選模式後，一輪對話內拿到 ≥ 8 個未過期、附連結與理由的機會
- 清單中每個截止日都標明來源（官方確認／未確認）
- 使用者資格不符的機會不出現在清單，且說明濾掉了什麼
- 不需要平台方任何伺服器在線

## 附錄：v2 爬蟲服務（獨立專案，另立 repo）

skill 版的天花板：web search 覆蓋不穩、每次都重搜、無法排程推播。v2 用爬蟲服務解決，**但只在 skill 版被用起來之後開工**。

- **職缺**：`JobProvider` 介面；JobSpy 包裝為 provider 之一；104 參考 boss-zhipin-scraper 的思路重新分析現行公開介面（優先找結構化 endpoint，不做 DOM scraping）
- **競賽**：依既有架構文件（BHuntrProvider 優先、WebDiscoveryProvider 取代逐校 parser、lazy verification、source evidence、canonical resolution、去重）
- **排序評測集**：上線前準備 20 筆機會 + 人工標準排序，作為排序品質的回歸測試
- **接口**：服務產出 JSON feed，opportunity-catch skill 檢測到 feed 可用時優先讀 feed、web search 降為補充——skill 介面不變，使用者無感升級
